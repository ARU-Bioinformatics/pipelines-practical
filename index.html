Pipelines and reproducibility

≈ 15 min

Turn a variant-calling analysis into a pipeline anyone can re-run with one command – with Snakemake and with Galaxy – and find out what an AI agent can and cannot prove about its results.

Claerbout’s principle
“An article about computational science in a scientific publication is not the scholarship itself, it is merely advertising of the scholarship. The actual scholarship is the complete software development environment and the complete set of instructions which generated the figures.”

J. B. Buckheit and D. L. Donoho (1995), WaveLab and reproducible research, summarising the principle of Jon Claerbout of the Stanford Exploration Project.

At the Stanford Exploration Project, Jon Claerbout and Martin Karrenbach set four basic rules for reproducible research: every result can be burned (deleted), built again, viewed, and its folder cleaned of intermediate files – each with one command. By the end of this practical your own analysis will pass the same test.

In the reads-to-variants practical you turned sequencing reads into variant calls, typing one command at a time. Could someone else – or you, in six months – get exactly the same calls again? Only if they know which data you used, every command and option, in which order, with which settings, and with which versions of the programs. A pipeline writes all of that down in a form a computer can run.

A project folder

≈ 20 min

Reproducibility starts before the first command: with a folder in which data, code, settings and results each have their place – and raw data that cannot change unnoticed.

Before the first command, decide where everything goes. A good layout keeps apart what you were given (data), what you write (code and settings) and what the computer makes (results) – so that anyone can see at a glance what can be regenerated and what cannot.

1.2 Bring in the data – and prove it is the same data

Activity 1.2 · Copy and checksum
  1. Copy the reads, giving them names that say which sample they are: cp /data/course/SRR098401_1.fastq data/raw/NA12878_R1.fastq && cp /data/course/SRR098401_2.fastq data/raw/NA12878_R2.fastq
  2. Copy the reference and its index: cp /data/course/hg19_CYP2C_slices.fa data/raw/reference.fa && cp /data/course/hg19_CYP2C_slices.fa.fai data/raw/reference.fa.fai
  3. Record a checksum of each file: md5sum data/raw/NA12878_R1.fastq data/raw/NA12878_R2.fastq data/raw/reference.fa > data/raw/MD5SUMS
  4. Compare your checksums with the ones published with the course data: cat data/raw/MD5SUMS /data/course/MD5SUMS
  5. Anyone can now check that their copies are identical to yours: md5sum -c data/raw/MD5SUMS
The reads now have new names. How do the checksums show that data/raw/NA12878_R1.fastq is still exactly the file SRR098401_1.fastq?

Both files have the same MD5 checksum, d2b8ddb488975fa5ef18e6e59edb5681. A checksum is calculated from the contents only – not the name or the date – and changing even one byte gives a completely different checksum. Same checksum = same data, whatever the file is called.

1.3 Protect the raw data

Activity 1.3 · Read-only
  1. Take away write permission from everyone (a-w): chmod a-w data/raw/*
  2. Look at the permissions: ls -l data/raw – -r--r--r-- means readable, not writable. (Compare ls -l /data/course: those files belong to root, so you could never change them.)
  3. Try an accident – writing over the reference: echo oops > data/raw/reference.fa
Why protect the raw data, but not the results?

Everything else is derived from the raw data: if it changes, every result and conclusion silently loses its foundation, and the data often cannot be obtained again. Results, on the other hand, are disposable: the pipeline can make them again at any time – so they are never edited by hand, and they need no protection. (Write protection prevents accidents; as the owner you could still change the permissions back.)

2.1 By hand

These are the steps of the reads-to-variants practical, with minimap2 for mapping. Run them one after the other and read what each one prints.

Activity 2.1 · Seven commands
  1. Folders for the results: mkdir -p results/mapped results/qc results/variants
  2. Map the read pairs to the reference and sort the alignments by position (about 5 s): minimap2 -ax sr -R '@RG\tID:NA12878\tSM:NA12878' data/raw/reference.fa data/raw/NA12878_R1.fastq data/raw/NA12878_R2.fastq | samtools sort -o results/mapped/NA12878.sorted.bam -
    -ax sr: short reads, SAM output; -R adds a read group naming the sample (\t means a tab); the final - tells samtools to read from the pipe.
  3. Index the BAM file: samtools index results/mapped/NA12878.sorted.bam
  4. Count the mapped reads: samtools flagstat results/mapped/NA12878.sorted.bam > results/qc/NA12878.flagstat.txt then head -5 results/qc/NA12878.flagstat.txt
  5. Call the variants: bcftools mpileup -f data/raw/reference.fa results/mapped/NA12878.sorted.bam -Ou | bcftools call -mv -Oz -o results/variants/NA12878.raw.vcf.gz
  6. Keep the confident calls: bcftools filter -i 'QUAL>=20 && INFO/DP>=5' -Oz -o results/variants/NA12878.filtered.vcf.gz results/variants/NA12878.raw.vcf.gz
  7. How many variants passed? bcftools view -H results/variants/NA12878.filtered.vcf.gz | wc -l
How many variants passed the filter?

15 of 60 raw calls.

A number is easy to compare, but it does not prove two files are the same. A checksum of the variant records does. (Checksum the records, not the file: the header of a VCF file records the date and time it was made, so two identical analyses never give identical files.)

2.2 A script – the simplest pipeline

Typing commands is slow and error-prone, and the only record is your shell history. Put them in a file instead: a bash script. Lines starting with # are comments; a \ at the end of a line continues the command on the next line.

workflow/run_all.sh
#!/bin/bash
# Variant calling for NA12878 – every step, in order (first version)
mkdir -p results/mapped results/qc results/variants

# 1. map the reads and sort the alignments
minimap2 -ax sr -R '@RG\tID:NA12878\tSM:NA12878' \
    data/raw/reference.fa data/raw/NA12878_R1.fastq data/raw/NA12878_R2.fastq \
    | samtools sort -o results/mapped/NA12878.sorted.bam -

# 2. index the BAM file, and count the mapped reads
samtools index results/mapped/NA12878.sorted.bam
samtools flagstat results/mapped/NA12878.sorted.bam > results/qc/NA12878.flagstat.txt

# 3. call the variants and keep the good ones
bcftools mpileup -f data/raw/reference.fa results/mapped/NA12878.sorted.bam -Ou \
    | bcftools call -mv -Oz -o results/variants/NA12878.raw.vcf.gz
bcftools filter -i 'QUAL>=20 && INFO/DP>=5' -Oz -o results/variants/NA12878.filtered.vcf.gz \
    results/variants/NA12878.raw.vcf.gz

echo "All steps finished."
Activity 2.3 · Run the script
  1. Press Create this file. Read it in the editor: it is exactly the commands you typed.
  2. Run it: bash workflow/run_all.sh – watch the time in the status bar under the terminal.
  3. Run it again: bash workflow/run_all.sh . Nothing has changed – what does the script do?
The second run redid every step. Why is that a problem for a real project – say 100 samples, when one new sample arrives, or when only the filter threshold changes?

A script has no idea what is already done: it cannot tell that the BAM files are up to date, so it repeats hours of mapping to change one threshold or add one sample. It lacks two things a workflow engine provides: dependencies (which file is made from which) and re-entrancy (continuing from where it stopped, redoing only what is needed). You could add checks by hand (“if the file exists, skip”) – but then an outdated file would never be updated.

2.3 When a step fails

A typo is all it takes. Break the script on purpose and see what it reports.

Activity 2.4 · A silent failure
  1. In the editor, change NA12878_R1.fastq in the minimap2 command to NA12878_R3.fastq (a file that does not exist) and save with Ctrl+S.
  2. Run it: bash workflow/run_all.sh – read all the output. Then ask the shell for the script’s exit status: echo $? (0 means success).
  3. Look at the results: ls -l results/mapped results/variants – compare the sizes with before. How many reads are in the new BAM file? samtools view -c results/mapped/NA12878.sorted.bam
minimap2 could not open its input – yet the script made new results and said “All steps finished.” Why did the later steps still “work”, and why is this dangerous?

minimap2 writes the SAM header before it opens the reads. So samtools sort received a valid header with no reads and wrote an empty BAM file (309 bytes, 0 reads, instead of about 500 kB). Indexing, flagstat, calling and filtering all ran without complaint on it and made empty results, and the script exited with status 0 – the status of its last command, echo. Nothing reports the failure: the results are simply wrong. Here they are conspicuously empty, but a failure halfway through a file – or one of two read files missing – gives results that look normal, and a report would say “no variants” where there are some.

Bash can be told to stop at the first error. Three settings, known together as strict mode:

set -estop as soon as a command fails
set -utreat a variable that was never set as an error
set -o pipefaila pipe (a | b) fails if any program in it fails, not only the last one
Activity 2.5 · Strict mode
  1. Add the line set -euo pipefail as the second line of the script (after #!/bin/bash), and save.
  2. Run the broken script again: bash workflow/run_all.sh then echo $? . Where does it stop now?
  3. Fix the typo (back to NA12878_R1.fastq), save, and run the script once more: bash workflow/run_all.sh
Without set -o pipefail, what is the exit status of minimap2 … | samtools sort … when minimap2 fails but samtools sort succeeds?
What a workflow engine adds

Strict mode stops a script at the first error – but it still cannot tell which files are up to date, it still redoes everything, and it leaves half-made files behind. A workflow engine such as Snakemake adds exactly what is missing:

  • dependencies – it knows which file is made from which;
  • re-entrancy – it redoes only what is needed;
  • clean failures – it deletes the output of a failed step so that nothing half-made is mistaken for a result;
  • a record – of what was run, when, with which code and settings.

3.2 The comma trap

Python
bad = ["NA12878" "NA12891"]     # oops: no comma between the two names

What is len(bad), and why?

1. With no comma between them, Python joins two strings that stand next to each other into one: the list holds a single item, 'NA12878NA12891'. There is no error message – it is a silent bug. Remember it: in a Snakefile, a missing comma between two input files glues their names together.

3.4 Making file names – the heart of Snakemake

Python
for s in config["samples"]:                 # repeat the indented line for each sample
    print(f"data/raw/{s}_R1.fastq")           # an f-string fills in {s}

pattern = "results/variants/{sample}.filtered.vcf.gz"
print(pattern.format(sample="NA12878"))       # .format fills in {sample} later – as Snakemake does

An f-string (f"…{s}…") fills in a value now; .format() fills in a pattern later. Snakemake works like .format(): your rules contain patterns such as results/{sample}.bam, and Snakemake fills in the sample when it knows which file you want. Snakemake’s expand() makes one name per value:

Python
from snakemake.io import expand

print(expand("results/variants/{sample}.filtered.vcf.gz", sample=config["samples"]))
print(expand("results/qc/{sample}.flagstat.txt", sample=["A", "B", "C"]))
What does expand("results/qc/{sample}.flagstat.txt", sample=["A", "B", "C"]) return?

A list of three file names: ['results/qc/A.flagstat.txt', 'results/qc/B.flagstat.txt', 'results/qc/C.flagstat.txt'].

Your first Snakefile

≈ 45 min

Describe each step as a rule – what it needs, what it makes and the command in between – and let Snakemake work out the order, run only what is needed, and keep a record.

A rule

A Snakefile is a set of rules. Each rule says how to make its output files from its input files – with a shell command, a Python script or a run block – and refers to its files as {input} and {output} in the command. Snakemake starts from the files you ask for (by default those of the first rule: its outputs – or, for a target rule such as all, its inputs), finds the rules that make them, then the rules that make their inputs, and so on – building a DAG (directed acyclic graph) of jobs.

4.1 The first rule

workflow/Snakefile
rule map_reads:
    input:
        "data/raw/reference.fa",
        "data/raw/NA12878_R1.fastq",
        "data/raw/NA12878_R2.fastq",
    output:
        "results/mapped/NA12878.sorted.bam",
    shell:
        "minimap2 -ax sr -R '@RG\\tID:NA12878\\tSM:NA12878' {input} | samtools sort -o {output} -"
The \\t inside the Python string becomes \t in the command, which minimap2 turns into a tab.
rule map_reads:a rule and its name (just a label), then an indented body
input:the files the rule needs – a list of strings, so commas between them
output:the files it makes
shell:the command. {input} becomes all the input files, in order, separated by spaces; {output} the output file
Activity 4.1 · Run a Snakefile
  1. Create workflow/Snakefile with the button above. (Snakemake finds workflow/Snakefile by itself.)
  2. “Burn” the results you made by hand – from now on the pipeline makes them: rm -r results
  3. Ask Snakemake what it would do – a dry run: snakemake -n . Find the job, and the reason it gives for running it.
  4. Run it, printing the command it runs (-p), on one CPU core: snakemake --cores 1 -p
  5. Run it again: snakemake --cores 1
The second run said “Nothing to be done”. Why?

Snakemake runs a job only if its output is missing, older than an input, or was made with different code, parameters, inputs or software than now (it keeps records in .snakemake/metadata) – or if you force it. This is re-entrancy: re-run a pipeline at any time and only what is needed happens.

# Summarise the filtered variants: a table of counts and a plot of call quality.
# Snakemake runs this script and gives it an object called `snakemake`
# with the rule's input, output, params, wildcards, ...
import gzip

import pandas as pd
import matplotlib

matplotlib.use("Agg")  # draw plots into files, not on a screen
import matplotlib.pyplot as plt

rows = []
for path in snakemake.input:
    sample = path.split("/")[-1].split(".")[0]  # results/variants/NA12878.filtered.vcf.gz -> NA12878
    with gzip.open(path, "rt") as vcf:
        for line in vcf:
            if line.startswith("#"):  # skip the header lines
                continue
            fields = line.rstrip("\n").split("\t")
            chrom, pos, ref, alt, qual = fields[0], int(fields[1]), fields[3], fields[4], float(fields[5])
            genotype = fields[9].split(":")[0]
            kind = "SNP" if len(ref) == 1 and len(alt) == 1 else "indel"
            rows.append({"sample": sample, "chrom": chrom, "pos": pos, "ref": ref, "alt": alt,
                         "qual": qual, "genotype": genotype, "type": kind})

variants = pd.DataFrame(rows)
summary = variants.groupby(["sample", "chrom", "type", "genotype"]).size().reset_index(name="variants")
summary.to_csv(snakemake.output.table, sep="\t", index=False)

fig, ax = plt.subplots(figsize=(6, 4))
for sample, group in variants.groupby("sample"):
    ax.hist(group["qual"], bins=20, alpha=0.7, label=sample)
ax.set_xlabel("Variant quality (QUAL)")
ax.set_ylabel("Number of variants")
ax.set_title("Quality of the filtered variant calls")
ax.legend()
fig.tight_layout()
fig.savefig(snakemake.output.plot, dpi=100)

The assistant called its single environment “fully reproducible”. What was wrong with it – and why does pinning bcftools and htslib exactly in one environment not help either?

It could not even be built. The bioconda builds of minimap2 2.22, samtools 1.17 and bcftools 1.10 were made against zlib 1.2 and need zlib older than 1.3, while Python 3.13 needs zlib 1.3.1 or newer – and an environment holds only one version of each library, so conda refuses (LibMambaUnsatisfiableError).

Without Python its pins are loose: bcftools=1.10 installs the newest 1.10.x (1.10.2), htslib is not mentioned so the solver picks the newest one that fits (1.21 today), and pandas and matplotlib have no version at all – exactly the colleague’s environment, with its different QUAL values.

Exact pins conflict too: htslib==1.10 for bcftools rules out samtools 1.17, which needs htslib 1.17 or newer. One environment for everything is fragile; pipelines give each step its own small, exactly pinned environment.

What is the difference between bcftools=1.10 and bcftools==1.10, and why pin htslib as well?

bcftools=1.10 means “any version starting with 1.10” – 1.10, 1.10.1 or 1.10.2 – and conda picks the newest, together with whatever htslib that build needs; bcftools==1.10 means exactly 1.10. The numbers come from the library as much as from bcftools itself, and the dependency ranges of old packages are sometimes widened later – which is how a 2020 build of bcftools came to be installed with htslib 1.21 – so pinning htslib==1.10 too fixes the part that actually changed the colleague’s results. The most exact records are a lock file of the package files (conda list --explicit --md5; Snakemake uses one saved as envs/calling.linux-64.pin.txt) or a container image; conda env export lists every package with version and build.

workflow/Snakefile
# =====================================================================
#  Variant calling for CYP2C19 / CYP2C9 – a reproducible pipeline
#  Run from the project folder:   snakemake --cores 1 --use-conda
# =====================================================================

configfile: "config/config.yaml"

SAMPLES = config["samples"]
REF = config["reference"]


# the target rule: the files we want at the end
rule all:
    input:
        expand("results/variants/{sample}.filtered.vcf.gz", sample=SAMPLES),
        expand("results/qc/{sample}.flagstat.txt", sample=SAMPLES),
        "results/report/variant_summary.tsv",


# 1. align the reads to the reference and sort the alignments
rule map_reads:
    input:
        ref=REF,
        r1="data/raw/{sample}_R1.fastq",
        r2="data/raw/{sample}_R2.fastq",
    output:
        "results/mapped/{sample}.sorted.bam",
    log:
        "logs/map_reads/{sample}.log",
    threads: 1
    conda:
        "envs/mapping.yaml"
    shell:
        "minimap2 -ax sr -t {threads} -R '@RG\\tID:{wildcards.sample}\\tSM:{wildcards.sample}' "
        "{input.ref} {input.r1} {input.r2} 2> {log} "
        "| samtools sort -o {output} - 2>> {log}"


# 2. index the sorted BAM file
rule index_bam:
    input:
        "results/mapped/{sample}.sorted.bam",
    output:
        "results/mapped/{sample}.sorted.bam.bai",
    conda:
        "envs/mapping.yaml"
    shell:
        "samtools index {input}"


# 3. mapping statistics
rule flagstat:
    input:
        "results/mapped/{sample}.sorted.bam",
    output:
        "results/qc/{sample}.flagstat.txt",
    conda:
        "envs/mapping.yaml"
    shell:
        "samtools flagstat {input} > {output}"


# 4. call variants
rule call_variants:
    input:
        ref=REF,
        bam="results/mapped/{sample}.sorted.bam",
        bai="results/mapped/{sample}.sorted.bam.bai",
    output:
        "results/variants/{sample}.raw.vcf.gz",
    log:
        "logs/call_variants/{sample}.log",
    conda:
        "envs/calling.yaml"
    shell:
        "bcftools mpileup -f {input.ref} {input.bam} -Ou 2> {log} "
        "| bcftools call -mv -Oz -o {output} 2>> {log}"


# 5. keep good-quality calls
rule filter_variants:
    input:
        "results/variants/{sample}.raw.vcf.gz",
    output:
        "results/variants/{sample}.filtered.vcf.gz",
    params:
        min_qual=config["min_qual"],
        min_depth=config["min_depth"],
    conda:
        "envs/calling.yaml"
    shell:
        "bcftools filter -i 'QUAL>={params.min_qual} && INFO/DP>={params.min_depth}' "
        "-Oz -o {output} {input}"


# 6. a table and a plot, made by a Python script
rule summarise:
    input:
        expand("results/variants/{sample}.filtered.vcf.gz", sample=SAMPLES),
    output:
        table="results/report/variant_summary.tsv",
        plot="results/report/variant_quality.png",

        "scripts/summarise_variants.py"

A graphical workflow engine

Galaxy (usegalaxy.org, usegalaxy.eu and many institutional servers) runs bioinformatics tools through web forms, keeps every dataset in a history with a full record of how it was made, and lets you build workflows by connecting tools on a canvas. James Taylor and Anton Nekrutenko began Galaxy at Penn State; it was first described in 2005. In James Taylor’s words: “Good ideas don’t have owners – they belong to everyone.”

The Galaxy tab is a practice server that works like Galaxy and runs the same WebAssembly programs as your terminal and your Snakefile.

Using AI in an analysis
  • Use AI to write and explain code you can read, run, test and keep – a Snakefile rule, a script – not to produce results you cannot check.
  • Never accept a result without provenance: which data, which software and version, which parameters – recorded by the process, not described afterwards.
  • Check AI output: run it, read the errors, look at file headers, compare checksums with a trusted run.
  • Say where AI was used (tool, version, for what) in your methods or README.
  • Never paste personal or patient data into an AI tool.

A rule

rule call_variants:                        # a name, a colon, an indented body
    input:
        ref=REF,                           # named inputs: {input.ref} in the command
        bam="results/mapped/{sample}.sorted.bam",   # {sample} is a wildcard
    output:
        "results/variants/{sample}.raw.vcf.gz",
    log:
        "logs/call_variants/{sample}.log",
    params:
        depth=250,                         # {params.depth}
    conda:
        "envs/calling.yaml"                # with --use-conda
    shell:
        "bcftools mpileup -d {params.depth} -f {input.ref} {input.bam} -Ou 2> {log} "
        "| bcftools call -mv -Oz -o {output} 2>> {log}"
# braces meant for the shell are doubled:  awk '{{print $1}}'
